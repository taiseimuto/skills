# Simple README

READMEを「プロジェクトに初めて来た人の入口」にする。読む人が、何をするものか、自分に関係するか、どう使い始めるか、詳しくはどこを読むかを判断できる状態を目指す。

## 成果物と作業範囲

- 既存READMEを改善するか、存在しなければ新規作成する。
- 必要な詳細だけを既存ドキュメントへ整理し、適切な置き場がなければ目的ごとのページを作る。
- 構造の理解に役立つ場合は、READMEに埋め込める編集可能なSVGを作る。
- 既存の言語・文書配置・利用者との合意を尊重する。このスキルの見出しや日本語を成果物に強制しない。
- 実装、依存関係、認証設定、デプロイ設定、エージェントの規約を変更する権限はこのスキルからは得られない。Git操作は対象リポジトリの規約と依頼範囲に従う。

## 1. 読み手と事実を先に確かめる

README、適用される作業規約、入口となるファイル、コマンド定義、設定例、既存docsを読む。READMEの古い説明だけを根拠にしない。

次の5点を短く整理してから構成を決める。通常は作業中の判断に使えばよく、別の計画書を増やす必要はない。

1. **種類**：アプリ、CLI、ライブラリ、バッチ、データセット、研究、文書、ハードウェア、またはその組み合わせ。
2. **主な読み手**：利用者、導入する開発者、運営者、共同研究者など。最初に助ける人を決める。
3. **最初の成功**：起動、1コマンド実行、1つの関数利用、サンプルの再現、目的の資料を開くなど。
4. **情報源**：コマンド・バージョン・入出力・接続先・公開範囲を裏付ける実装や設定。
5. **既存の詳細ページ**：そのまま案内できるもの、移動するもの、現在の実装と矛盾するもの。

例：Webならルートと認証、CLIなら実行入口と`--help`、ライブラリなら公開APIと使用例、データ処理なら入力・変換・出力、資料なら読書順と成果物を確認する。

- 不明な仕様やサービスの接続を補って作らない。ライブラリや外部サービスの仕様が必要なら、その環境で使える公式ドキュメントやドキュメント検索を使う。
- ローカルの調査で解けない重要な前提だけ確認する。任意の好みは妥当な判断で進める。
- 更新日、稼働中案件、教材件数など、説明の理解に不要で陳腐化しやすい情報は入口から外す。

## 2. 情報を残す・移す・削る

各まとまりを、次の基準で判断する。

| 判断                       | 基準                                                   | 例                                                       |
| -------------------------- | ------------------------------------------------------ | -------------------------------------------------------- |
| READMEに残す               | 初見の人が用途を判断し、最初の成功に到達するために必要 | 目的、主な使い方、必要条件、短い実行例、出力例           |
| 詳細へ移す                 | 特定の担当者や特定の場面で必要。まとめて読む価値がある | 本番設定、全環境変数、管理API、障害対応、データ移行      |
| 既存文書へリンク           | すでに詳細の置き場があり、同じ説明を複製する必要がない | 教材執筆、運用手順、認証設計、コントリビューション       |
| 削る・訂正する             | 重複、古い説明、実装の実況、現在の利用者に不要な履歴   | 過去の修正経緯、内部関数一覧、全画面・全テーブルの棚卸し |
| エージェント用文書に委ねる | コーディング時だけ必要な指示                           | 必須ガード関数、禁止実装、作業順序、テストの対応表       |

エージェント向け規約が既存文書にある場合はREADMEから重複を消す。READMEにしかない現行の規約は黙って捨てず、既存のエージェント用文書へ保存するか、規約変更が許可されていなければ要確認点として残す。スキルの適用を理由に既存規約を上書きしない。

**最初の操作に直結する制約はREADMEに残す。** 例：認証の前提、別途取得するデータ、対応OS、サンプル実行の前提、初期化による上書き。「詳細へ移した」ことを理由に必要な注意まで隠さない。

分離先は「ローカル開発」「本番運用」など読者の用事で分ける。短い補足だけのページ、旧READMEの丸ごと退避、巨大な「その他詳細」は作らない。移動後に両方の説明を残さず、リンクを入口にする。

境界が迷う場合は [references/editorial-examples.md](references/editorial-examples.md) の判断例を読む。

## 3. 入口として組み直す

次の候補から、そのプロジェクトに必要なものだけ選んで並べる。固定テンプレートとして全部を追加しない。

- **名前と説明**：何を、誰のためにするものかを1〜3文で示す。
- **利用の入口**：サービスURL、インストール先、配布物、資料の入口など、実在するものだけ。
- **できること・使い方**：読む人の行動でまとめる。画面・コマンド・公開APIなどは必要な代表例だけ。
- **構成または処理の流れ**：図で理解が早まる場合に置く。
- **技術・動作環境**：導入や開発の判断に必要な粒度。依存パッケージの一覧は不要。
- **最短の実行例**：必要条件 → 準備 → 実行 → 何が起きるか。コピーして試せる順にする。
- **開発**：利用者向けの導入手順とは違う場合に分ける。よく使うコマンドを絞る。
- **関連ドキュメント**：次の用事が分かる名前で案内する。
- **ライセンス・引用・データ利用条件**：既存の重要情報を維持し、用途上必要なら目立つ位置に置く。

編集の基準：

- 見出しを追うだけで概要が分かるようにする。短い文章、比較表、実行例を使い分ける。
- 表は同種の情報の比較に使う。長文をセルに詰めない。列挙が長くなったら分類か分離を見直す。
- ディレクトリ図は、初見の人が主要な置き場を見つけるために役立つ場合だけ載せる。内部ファイルを網羅しない。
- 固定の行数目標や削減率で切らない。目安は入口を数分で読める量だが、必要な使い方を省略して達成しない。
- 本番を変更する例、破壊的な初期化、非公開データに依存するseedを最初のコマンドにしない。
- 空の環境で始められる経路があるならそれを基本にする。設定や認証が必要なら実行例より前に示す。
- 実行結果がURLとは限らない。CLIなら標準出力、ライブラリなら戻り値、パイプラインなら生成物、資料なら読む順序を示す。

## 4. 図が必要ならSVGで作る

ユーザーが求めた場合、または複数の要素と関係が文章より伝わる場合に図を追加する。単一機能の小さなツールや文書だけのリポジトリに、架空のインフラ図を足さない。

**図を作るときは [references/svg-diagrams.md](references/svg-diagrams.md) を読む。** ここに、図の種類、ロゴの扱い、配置寸法、矢印の意味、ブラウザでの確認基準をまとめている。[assets/flow-starter.svg](assets/flow-starter.svg) は汎用的な入出力図の出発点として必要なら使う。

図の要点：

- 実装から分かる要素だけを描く。図の種類はシステム構成、実行フロー、データ処理、成果物の依存関係などから選ぶ。
- ブランドロゴがある要素には確認できる素材を使う。ロゴがない要素は文字と簡単な図形で十分。
- ノード名と役割を両方書く。矢印の意味、実行環境、保存先の区別をはっきりさせる。
- SVGをリポジトリに保存し相対パスで埋め込む。外部画像、JavaScript、外部フォント、`foreignObject`に依存させない。
- 図と本文で同じ説明を繰り返さず、本文は図だけでは伝わらない補足に使う。

## 5. 完了前に確認する

- **入口**：初見の人が「何のためのものか」「どう使い始めるか」「続きはどこか」に答えられる。
- **事実**：代表コマンド・パス・前提・入出力が実装や既存の確かな情報と一致する。使用例を推測で創作していない。
- **初回利用**：必要条件が先に書かれ、Git管理外のファイルや暗黙の認証設定で詰まらない。
- **分離**：必要情報を失わず、詳細ページに到達できる。重複やリンク切れ、古い相互参照を残していない。
- **書式**：相対リンク・画像参照・コードフェンス・見出しを確認する。Git管理下では`git diff --check`も使う。
- **図**：SVGがある場合は次の検査に加え、ブラウザで画像として埋め込んだ表示を確認する。スクリプトの成功だけで見やすさを保証しない。

```bash
python3 <このスキルの場所>/scripts/check_svg.py <作成した図.svg>
```

READMEだけの変更にアプリ全体のビルド・テストを機械的に要求しない。コマンドの実在確認とリンク・表示の検証を行い、安全な試行が有益なときだけ実行する。実施していない確認を実施済みと報告しない。

結果は、情報の整理方針、成果物へのリンク、実施した検証、未確認点があればその範囲を簡潔に伝える。利用できるツールは環境ごとに選び、特定のAI製品・MCP・ブラウザ実行ツールを必須にしない。
