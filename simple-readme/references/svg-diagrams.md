# READMEに載せるSVG図

## 描くものを選ぶ

最初に「この図で読み手が理解する関係」を1文で決める。主要要素を4〜8個程度にまとめることを出発点にし、数を満たすために要素を作らない。

| プロジェクト | 図が答える問い | 形の候補 |
| --- | --- | --- |
| ホストされたアプリ | どこで動き、どこへ保存し、何と連携するか | アプリを中央、利用者を左、保存先を右、外部連携を下 |
| CLI・ビルドツール | 何を入力して何を得るか | 入力 → ツール → 生成物 |
| ライブラリ | 呼び出し側と公開API・外部依存がどう関わるか | 呼び出し側 → 公開API → 依存先。必要な場合だけ |
| データ処理・研究 | データがどの段階を経て成果物になるか | データ → 前処理 → 実行 → 結果 |
| 文書・教材 | 何をどの順で読むか、前提は何か | 読書順・依存図。単純な一覧なら図を作らない |
| ハードウェア | 部品間の信号・電源・処理の関係は何か | ブロック図。電源線と信号線の意味を区別 |

構成図にデプロイ手順や全APIを重ねない。実行フローなら処理順、構成図なら環境・接続関係に焦点を合わせる。

## 内容の正確さ

描く前にノード名、役割、根拠、接続先、矢印の意味を確かめる。存在するが利用されていない依存パッケージを、稼働中のサービスとして描かない。

- クラウド、端末、CI、外部サービスなどの境界は薄い囲みとラベルで示す。同じ提供元でも境界が異なるものを一括りにしない。
- 保存先が用途で分かれる場合は、細かいDBテーブルではなく「業務データ」「成果物」「同意記録」のような目的を示す。
- **矢印の意味を混ぜない。** データの流れ、APIを呼ぶ向き、実行の順番のどれかを選び、必要なら凡例で明示する。
- レスポンスが返ることだけを理由に、全接続を両矢印にしない。独立した送受信、読み書きなどを表す場合に使う。
- 署名付きURLで利用者が直接ストレージへアクセスするなど、説明に重要な経路を単純化する場合は、図の範囲を「主要な連携」「アプリからの通信」などと示す。
- 小さな周辺連携は本文で補ってよい。省略すると誤解する重要な入力や出力は省かない。

## ロゴ素材

1. まず既存リポジトリの素材か公式ブランドキットを確認する。
2. 適切な素材がなければDevicon、Simple Iconsなど、出典と利用条件を確認できる配布元を使う。ツールがなければ、利用可能なWeb閲覧・HTTP取得手段でよい。
3. 実ファイルの内容を確認し、ブランド形状を想像して手描きしない。見つからない場合はサービス名を文字で表示する。
4. 配布元のブランドガイド、色、縦横比、必要なライセンス表示を尊重する。各素材のライセンスが同じとは限らない。
5. ロゴのベクターをSVG内に埋め込み、`symbol`と内部参照または`g`で配置する。外部URLの`image`参照は使わない。
6. 出典URLと必要なライセンス表示をSVGのコメントまたは既存のクレジット文書へ保存する。READMEに素材一覧を増やさない。

素材を埋め込むときは、元の`viewBox`、`fill`、`stroke`、`fill-rule`、マスクなども保つ。内部IDがある複数素材はIDを名前空間化し、`url(#…)`や`href`を一緒に修正する。取得したSVGのスクリプトや外部参照をそのまま持ち込まない。

## 見た目の基準

今回のような読みやすさを再現する出発点。数値は構造と文字量に合わせて調整する。

| 要素 | 目安 |
| --- | --- |
| キャンバス | 横960〜1120、縦400〜720程度の`viewBox`。内容に応じて変更 |
| 背景 | 白などの不透明な明るい背景。ダーク表示でも文字を保つ |
| 配色 | 本文は墨色、補足は読み取れる灰色、線は落ち着いた灰色。ブランドロゴの色は保持 |
| ノード | 白地、細い枠線、角丸10〜14。影やグラデーションは通常不要 |
| 余白 | 外側24〜40、カード内20〜24、カード間40以上を起点にする |
| 文字 | ノード名20〜23、役割16〜18、補足14〜16程度 |
| ロゴ | 主に28〜36程度。提供元の余白・最小サイズの指定を優先 |
| 接続線 | 太さ1.5〜2程度、直交線中心、分かる矢印。交差と長い迂回を避ける |
| 囲み | 実行環境など意味のあるまとまりだけ。薄い塗りと細い破線などで区別 |

装飾より、名前・役割・関係を同時に読めることを優先する。色やロゴだけで区別しない。カードの高さを文字量に合わせ、長い文は行を分ける。SVGの`text`は自動改行しないため、座標を分けた`text`か`tspan`を使う。

矢印はカードの背後に描き、端を枠に合わせる。接続の線を共有する「バス」は、サービス同士がつながっていると誤解させる場合には使わない。両矢印には`orient="auto-start-reverse"`など、始端と終端が正しく向くマーカーを使う。

## ファイルと埋め込み

- 既存の図の保存場所を優先する。なければ`docs/assets/`などへ意味のある名前で保存する。
- ルートに`xmlns`、`viewBox`、`role="img"`を置き、`title`と`desc`を`aria-labelledby`で関連付ける。
- `desc`には図の主要な要素と関係を文章で書く。ロゴ名を並べるだけにしない。
- READMEは相対パスの画像として埋め込み、意味が分かる代替文を付ける。本文の小さな注記にだけ重要な仕様を閉じ込めない。
- JavaScript、イベントハンドラ、外部フォント、`foreignObject`、外部画像、外部CSSに依存させない。
- 汎用素材が必要なら[flow-starter.svg](../assets/flow-starter.svg)を複製して調整する。これは完成図でも、Webアプリの雛形でもない。実際のノード・ラベル・境界に置き換える。

```markdown
![入力データをツールで変換し、検査済みの成果物を出力する流れ。](docs/assets/workflow.svg)
```

## 確認

```bash
python3 <このスキルの場所>/scripts/check_svg.py <作成した図.svg>
```

この検査はXML構文、内部参照、代替説明、外部依存などを確認する。意味の正しさ、見た目、ブランドの利用条件を判定するものではない。

利用できるブラウザまたは描画ツールで、次を実際に確認する。

1. 単体SVGが描画される。
2. HTMLの`img`など、README同様の画像埋め込みでもロゴと線が描画される。インラインSVGだけで確認を終えない。
3. 実際に表示される幅（GitHubならおおむね800〜1000px）で、ラベルが読める。文字の切れ、重なり、矢印の隠れがない。
4. 小さい画面でも主要な流れが追える。縮小で全て読ませようとして文字を増やさず、必要ならクリックして拡大できる図として扱う。
5. 明るい背景・暗い背景の上に画像として置いても、背景と文字のコントラストが保たれる。

ブラウザやレンダラーを使えなければ、構造検査まで実施し、視覚確認は未実施と明示する。未確認の図を「表示確認済み」にしない。
