# 再現性の確認シナリオ

スキルを更新したとき、または別のエージェントで試すときに使う。実在する対象の実装・設定を読み取らせ、編集結果を次の観点で確認する。全ケースで同じ見出し・同じ文章になることは合格条件ではない。

試行は許可されたローカルのコピーで行う。ここにある架空のコマンドや構成を実際のプロジェクトへ持ち込まない。

## A. 運営用Webアプリ

依頼：「READMEが長くて読めない。必要な情報に絞り、サービスのロゴを使ったSVG構成図を追加して。」

対象の特徴：アプリ、DB、ファイル保管、メール送信、外部認証。READMEに画面全件・管理API・本番設定・ガード関数の規約が混在。初期データはGit管理外。

合格の目安：

- 概要、主な利用者、実際の起動方法と前提が先に分かる。
- 管理API・本番設定は目的ごとの既存ページまたは新ページへ。現行の重要情報を失わない。
- Git管理外の初期データを必須の最初のコマンドにしない。
- 図は確認できたサービスと役割を示し、ロゴは埋め込み。外部依存検査と画像表示確認を行う。

## B. ローカル完結のCLI

依頼：「このCLIのREADMEを初めて使う人にも分かりやすくして。」

対象の特徴：サポート対象OS、インストール手順、実在するサンプル入力、標準出力またはファイル出力。クラウドや認証はない。全フラグとプラグイン作者向けの説明が長い。

合格の目安：

- 導入 → 代表的な実行 → 結果が分かる。
- 全フラグは既存ヘルプや詳細へ。利用者とプラグイン作者の手順を分ける。
- 存在しないサーバー・DB・OAuthを図や環境変数に追加しない。
- 図が理解を助ける場合だけ入出力図を使い、単純なら図なしで完了する。

## C. 公開前のライブラリ

依頼：「このライブラリのREADMEを整理して。使用例を優先して。」

対象の特徴：ローカルで利用可能な公開APIはあるが、パッケージレジストリには未公開。内部クラス一覧と開発ログが先頭にある。

合格の目安：

- 未公開である事実を保ち、確認できるローカル導入方法と公開APIの例を使う。
- 関数名や引数、戻り値を実装または実行結果で裏付ける。
- 最小利用例を内部設計より先に置く。架空のインストール方法を案内しない。
- ライセンスや互換性の重要情報を保持する。

## D. 研究・データ処理

依頼：「他の研究者が再現しやすいREADMEにして。処理の流れも図にして。」

対象の特徴：非公開データが別途必要。小さなサンプルはリポジトリにある。全件実験にはGPUと長時間の計算が必要。利用条件と引用形式がある。

合格の目安：

- 目的、データの入手条件、環境、サンプルでの再現、生成物の場所が分かる。
- 図はデータ → 前処理 → 実行 → 結果を実装に合わせて示す。
- 許可なしに全件計算を始めず、サンプルの確認と本実験の区別を報告する。
- 利用条件と引用形式を、内部メモとして削らない。

## E. 文書・教材集

依頼：「人が読む資料にたどり着きやすいREADMEにして。」

対象の特徴：MarkdownとPDFが中心。閲覧には開発環境が不要。任意のPDF生成スクリプトがある。READMEは生成手順と執筆ルールばかり。

合格の目安：

- 対象読者、主要資料へのリンク、読む順序が先に分かる。
- 閲覧の前提としてNode.jsやPythonを要求しない。
- 生成手順は貢献者向けに分離。架空の技術スタックやシステム図を足さない。

## F. 明示条件を尊重する

依頼：「READMEだけを編集して。別ファイルは作らない。図も不要。」

対象の特徴：詳細ページは既存。READMEにしかない重要な運用注意もある。

合格の目安：

- READMEだけを編集し、図・新規詳細ページ・エージェント規約を追加しない。
- 既存の詳細ページへ案内しつつ、移動できない重要な注意は簡潔に残す。
- 行数削減のために必要な情報を黙って捨てない。

## 評価の記録

確認したケースと、実際の成果物・実施した検証を記録する。プロンプト例を読んだだけなら「動作確認済み」としない。次の失敗は修正対象にする。

- 誤ったコマンド、架空のサービス、壊れた入口、重要な利用条件の欠落。
- 詳細の丸ごと退避だけで、読み手がどこへ進むか分からない。
- 図の出典を確認せずロゴを手描きする、外部画像に依存する、ブラウザ未確認を確認済みとする。
- 特定のホスティングやAIエージェントがなくてもできる作業を、そのツールの有無で止める。
